## Decision 2 — state and reducer

The plan: "State is a single `useReducer` over `{ included: ObsId[], question: number, forge: ForgeChoice | null }`". Two readings, both decided here:

- **`custom` is a fourth field.** The plan asks for a custom builder (quantity, at most/at least/exactly/between, number) and for exactly those three state fields; the builder's typed text has to live somewhere, and keeping it in the reducer lets it survive a switch to a menu question. `question` is an index into the five-item menu, or `CUSTOM_QUESTION` (5) for the builder. A deviation by addition, not removal.
- **`ForgeChoice` is the single value `"raise-upper-bound"`.** The plan's forge picks its own target ("the established upper bound of the answer's ruling if that bound is finite and cites support, else of the first draft claim that has such a bound, and is disabled if none does"), so the state records only that the forge is on; the target is found from the engine's Brief on each computation (`forgeTarget`). Any change of documents or question clears the forge (pinned: "toggle, ask, custom edits and presets clear the forge…" in `compute-demo-view.test.ts`).

There are six scripted-step buttons (the domain's `CANON_SCRIPT`, pinned equal to the page's presets by "the presets are the domain's CANON_SCRIPT, step for step"). The initial state is step 1.

## Decision 3 — what the page derives itself, and each thing the plan names

The brief's rule: any derivation the page does itself must be named by the plan. Quoted from the M8 scope, with where it lives:

1. **The forge** (`forgeTarget`, and the tampering in `forged`): "it raises by one the established upper bound of the answer's ruling if that bound is finite and cites support, else of the first draft claim that has such a bound, and is disabled if none does — feeding `recheck`". Checked, in all 80 states, against a re-read of the engine's own Brief written in the test, not against `forgeTarget` ("in every state where the control is enabled, forging makes recheck report bound-differs…").
2. **The pairwise table** (`pairwiseOf`): "a **pairwise table** computed by calling `ground` on every pair, triple and the full set ("6 of 6 pairs consistent · 4 of 4 triples consistent · all four: conflicted"), so the headline fact is computed on screen, not asserted". It runs `ground` on every subset of the included documents of size two up to the whole set, and counts. It appears when the question's ruling is `conflicted`. Each row is checked against `ground` and against the oracle ("with all four documents: 6 of 6 pairs consistent…").
3. **The custom question** (`customQuestion`): "a custom builder (quantity · at most/at least/exactly/between · number)". It turns the builder's text into a `Claim` (`at most n` is `[null, n]`, `at least n` is `[n, null]`, `exactly n` is `[n, n]`, `between a and b` is `[a, b]`) and hands it to `answer` like a menu claim. Text is read as an integer only if it is digits with one optional minus, at most 12 digits; anything else is `custom-invalid`. Everything else about the claim (a range with the ends reversed, a claim the schema already implies, a magnitude) is the engine's refusal. Pinned: "a sweep of valid questions over all 16 subsets…" and the refusal tests.
4. **The highlighted support ids** ("the support ids highlighted on the evidence list"): each document's "cited by" is the set of cards whose `support` or `core` names it, read from the engine's rulings, deduplicated (the first version of this listed a card twice when a document supported both of its bounds; "the documents each ruling cites are highlighted on the evidence list…" found it).

Not named by the plan, display only, and said so: the labels (`SHORT`: "packing", "transit", "customs", "delivery"; the menu is the domain's own labels), the one-line gloss per kind (`KIND_GLOSS`), `rejectionText` (the sentences for a refused question: `lib/entail` renders the faults of draft claims, not of a question), `intervalText`, the "the chatbot said 2 days (a typical figure…)" line, and `draftPositions`, the map from a ruled claim back to its draft position, which exists because `answer` drops a refused claim. Every ruling sentence on the page is `renderEntailment`'s, and the Brief text is `renderBrief`'s, printed as they are.

## Decision 4 — the drift guard, and what a mark-done pull request must change

`app/milestones.ts` holds `{ id, title, done }` for M1 to M9. `done` is the only status: DONE.html's `todo` and `wip` are both "not done" to a stranger and the test does not compare them. `currentMilestone()` is the first milestone not done; `progressLine()` is the footer's sentence, built from the list. `app/page.tsx` has no literal about a milestone: pinned by "neither page.tsx nor the demo component has a string literal that names a milestone or a count of them", which reads the parsed string and JSX-text literals (and has a tooth).

`app/milestones.test.ts`:

- The guard is the function `findDrift(list, html)`. **Its teeth are hermetic.** Each builds its own agreeing pair: the real DONE.html text with every pill set to `todo`, then chosen rows flipped with `flipPill`, which throws if the html does not change or the row does not exist ("flipPill throws when it changes nothing…"), against the real list's ids with chosen entries done. So a regex miss cannot make a tooth vacuous, and no tooth depends on the real DONE.html being in a particular state.
- "both sources moved together is not a disagreement": M1 to M8 in both; then every milestone in both.
- A pair where only DONE.html moved, a pair where only the list moved, a dropped row, a wip pill (not compared), and markup the parse does not recognise (not a vacuous pass).
- **One** test reads the real list against the real file: "claims exactly the same milestones done in both places". Another asserts the real parse: "DONE.html parses to nine milestone rows, M1 to M9 in order…".

**A `chore(genesis): mark MN done` pull request must change exactly two things, together:** (1) in `.genesis/DONE.html`, the pill of row MN becomes `<span class="pill ok">done</span>`; (2) in `app/milestones.ts`, `done: false` of entry MN becomes `done: true`. Nothing else in `milestones.ts`, nothing in the test, no sentence on the page. The page's footer then follows from the list. **Simulated in a scratch copy of this branch** (the full suite, `npx vitest run`): M8 flipped in both files: 3272 passed, 0 failed of 3272; M8 and M9 flipped in both: 3272 passed, 0 failed of 3272; M8 flipped in `milestones.ts` only: 1 failed (`milestones.test.ts`: "claims exactly the same milestones done in both places"); M8 flipped in `DONE.html` only: 1 failed (the same test).

## Decision 5 — the banned-hook scan and the import confinement

The plan: "a source scan (parsed, not grepped) for the banned hooks" and "no `useEffect`, `useCallback`, `useMemo`, `setTimeout` or `async` anywhere". `components/order-desk/__tests__/support/scan.ts` walks the parsed tree (TypeScript 7's `typescript/unstable/sync`, as M1's scans do) of every non-test source of `components/order-desk`, `app/page.tsx`, `app/milestones.ts` and `app/layout.tsx`. The inventory is exact and a code file of a kind it cannot parse (`.js`, `.jsx`, `.mjs`, `.cjs`, `.mts`, `.cts`, `.d.ts`) is itself red ("the inventory is exactly the files this milestone expects…"). It reports: `useEffect`, `useLayoutEffect`, `useInsertionEffect`, `useCallback`, `useMemo`; React's `use`; `setTimeout`, `setInterval`, `setImmediate`, `queueMicrotask`, `requestAnimationFrame`, `requestIdleCallback`, `MessageChannel`; `Date`, `performance`, `crypto`, `fetch`, `XMLHttpRequest`, `WebSocket`; `Math.random`; `Intl`; `toLocale*` and `localeCompare`; `new Function`; `eval`; `Promise`; `await`; `for await`; the `async` modifier; and dynamic `import()`; and the same names as string keys. It over-reports on purpose (any identifier spelled like a banned name), which fails closed. A file that does not parse is a violation.

**Every rule has a planted fixture that trips exactly its rule** (41 fixtures, in "the scan's teeth…"; a test fails if a name in the scan's table has no fixture). **What it does not see is planted too and passes clean** (nine "NOT SEEN (a limit, pinned)" fixtures): a name built at run time (`globalThis["set" + "Timeout"]`, `R["use" + "Effect"]`), `Reflect.get(globalThis, "Date")`, an alias of `Math` and `(0, Math).random()`, a thenable with no `Promise` or `await`, `process.nextTick`, `localStorage`, `structuredClone`. These are examples, not a complete list.

**Import confinement.** "the only file under `components/` that imports `lib/**`/`domains/**`" is pinned by the parsed import specifiers (static, `import type`, `export … from`, `import()`, `require()`, `import x = require()`; each form has a fixture): only `compute-demo-view.ts` reaches `lib/`, `domains/`, `scripts/`, `tests/` or `.genesis/` ("only compute-demo-view.ts imports lib/** or domains/**…"). The component's only React import is `useReducer`, called once; `OrderDeskDemo.tsx` starts with `"use client"` and `page.tsx` does not ("OrderDeskDemo.tsx is a client component…").

## Decision 6 — comparisons are of full contents

The page must "show the same Brief as `npm run demo:order-desk` for the same step". The test compares, for each of the six scripted steps, the page's paragraph, its rendered Brief text, and every card against the demo's ruling on these fields: kind, sentence, support (both sides, ids), core, each open end's quantity and side, and the cut — not seq or kind alone (`cardDifferences`). The recheck verdict of each position is compared with the demo's finding. **Not compared by `cardDifferences`:** the card's "the chatbot said…" line (pinned for step 1 only, by a render test: "step 1's cards show the cut, the open ends on both sides, and what the chatbot said…") and the text of the recheck line (pinned for the forged ruling's `bound-differs` text, and by the formatter's own tests). It has teeth: a card with the same kind and the same position and a different core, a different support, a different sentence, an open end with the same count and a different side, or a different cut is reported ("TEETH: a card with the same kind and the same position but different contents is reported…"). The same comparison runs against the engine called directly in all 80 states ("the bridge's composition equals the engine's, called directly, in all 80 states…").

## What is not proven, and what no test pins

- **Button-to-action wiring is not pinned.** Which `dispatch` each checkbox, radio, select, text input and button calls is not exercised by any test: the node environment has no click path (no jsdom, by the plan). The reducer those controls call is pinned. The plan assigns the click path to a manual run against the live URL, recorded in `docs/WALKTHROUGH.md` (M9). In this session the click path was driven by hand against a local `next start` (steps 4 and 5, ticking `o3` and `o4`, the forge) and it worked; that is an observation, not a test.
- **Hydration.** Server rendering is deterministic (the markup of all 80 states is identical on two renders: pinned), and a production build served locally had no console message; that the client's first render equals the server's is not pinned by a test.
- **Layout is not pinned.** The stylesheet is read as text (44 px minimum heights on the button, document label, choice label, select and text input; a `:focus-visible` outline; every colour token redefined for dark; one column below 52 rem). No layout engine runs in a test. 375 px (no horizontal scroll at step 1 and step 5, no target under 44 px) and the light and dark themes were checked by hand in a browser against the local production build; colour contrast was not measured.
- **Accessibility beyond static structure is not pinned:** headings, labels, a fieldset with a legend, a captioned table with column and row headers, and a status line are pinned as markup; keyboard operation is the browser's native handling of inputs and buttons and was not tested; screen-reader behaviour was not tested.
- **Untested branches.** The rendering of a draft claim refused before ruling (`refused`) and the engine throwing inside `computeDemoView`'s `try` are not reachable from any state this page can build with the drafter as it is; the first is recorded by a test that asserts it never happens in the 80 states, the second is "stated, not pinned by a test" (the `try` is exercised by a state whose getter throws, which is the same `catch`). A magnitude above `MAX_MAGNITUDE` is unreachable from the builder (12 digits is below 2^40), so the engine's refusal of it is not exercised through the page.
- **Card text not compared.** The card's "the chatbot said…" line is pinned for step 1 only, and the text of each recheck line is pinned for the forged ruling and in the formatter's tests, not across the 80 states (Decision 6).
- **The oracle.** `support/oracle.ts` enumerates worlds with a cap of 40; it is exact for every question used here (largest constant 14, custom sweeps at most 12). A custom number above the cap would need the cap raised.
- **The drafter is a stand-in.** The left column is not a language model; it is M6's fixed rule, pinned there. The page says so.
- **DONE.html's M8 row says** "deployed URL renders the same Brief as the last step of `npm run demo:order-desk`". That is stale wording (the amended check is step 5, the conflict). It was not edited here; the mark-M8-done pull request is where it is fixed. The page itself makes no such claim.
